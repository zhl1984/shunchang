# 数清标注平台

数清标注平台是一个基于 Vue 3 的 Web 管理平台前端项目。当前阶段以搭建稳定、易维护的管理端基础能力为目标，具体标注业务暂不纳入项目范围。

平台预计包含大量表单、卡片和表格页面，并需要支持国际化与主题切换。

> 项目基础工程已初始化，具体业务模块尚未开始开发。

AI 编程工具参与开发前应先阅读 [`AGENTS.md`](./AGENTS.md) 中的项目开发约定。

## 技术栈

项目计划采用以下技术方案：

| 分类         | 技术           | 建议版本基线 | 用途                                                   |
| ------------ | -------------- | ------------ | ------------------------------------------------------ |
| 核心框架     | Vue            | `3.5.x`      | 构建用户界面，使用 Composition API 与 `<script setup>` |
| 开发语言     | TypeScript     | `5.8.x`      | 提供静态类型检查                                       |
| 构建工具     | Vite           | `6.x`        | 本地开发与生产构建                                     |
| 状态管理     | Pinia          | `2.3.x`      | 管理跨页面和全局状态                                   |
| 路由         | Vue Router     | `4.5.x`      | 页面路由与导航守卫                                     |
| HTTP 客户端  | Axios          | `1.8.x`      | 请求后端接口                                           |
| UI 组件库    | Ant Design Vue | `4.2.x`      | 表单、表格、卡片等管理端组件                           |
| CSS 预处理器 | Less           | `4.2.x`      | 样式组织和通用工具类生成                               |
| 包管理器     | Yarn           | `1.22.x`     | 依赖安装与脚本管理                                     |

版本选择以成熟、兼容和便于维护为原则。正式初始化时应锁定依赖版本并提交 `yarn.lock`，后续升级需经过兼容性验证。

## 项目目标

- 建立统一的管理端页面布局和导航体系。
- 沉淀可复用的表单、表格、卡片及查询区域组件。
- 支持复杂表单校验、动态表单和表单状态管理。
- 支持表格查询、分页、排序、筛选和批量操作。
- 统一封装接口请求、异常处理和用户提示。
- 首期仅支持简体中文，同时保留后续扩展国际化的能力。
- 支持浅色、深色及后续自定义主题。
- 保持严格的 TypeScript 类型约束和清晰的模块边界。

## 基础能力规划

### 页面布局

- 顶部导航栏
- 侧边菜单栏
- 面包屑导航
- 多级路由页面
- 响应式内容区域
- 可选的标签页导航

### 表单

- 统一表单布局和校验规则
- 查询表单与编辑表单
- 动态增减表单项
- 表单数据回显与重置
- 异步选项加载
- 提交防重复处理

### 表格

- 服务端分页、排序和筛选
- 列配置与自定义渲染
- 行选择与批量操作
- 固定列和横向滚动
- 加载、空数据和异常状态
- 表格查询条件与 URL 或页面状态同步

### 卡片

- 信息概览卡片
- 数据统计卡片
- 带操作区的内容卡片
- 统一间距、阴影和响应式布局

### 国际化

计划使用 `vue-i18n` 实现国际化，首期仅维护简体中文语言包，后续按需增加其他语言。页面文案、菜单、表格列名、表单标签、校验提示及接口错误提示应避免直接硬编码。

### 主题切换

主题能力基于 Ant Design Vue 的设计令牌与 CSS 变量实现，计划支持：

- 浅色主题
- 深色主题
- 跟随操作系统
- 主题偏好本地持久化

## 建议目录结构

```text
src/
├─ api/               # 接口定义与请求方法
├─ assets/            # 图片、字体及全局样式
├─ components/        # 通用组件
├─ composables/       # 可复用组合式函数
├─ constants/         # 常量与枚举
├─ directives/        # 自定义指令
├─ layouts/           # 页面布局
├─ locales/           # 国际化语言包
├─ router/            # 路由配置与守卫
├─ stores/            # Pinia 状态模块
├─ styles/            # 主题和公共样式
├─ types/             # 公共 TypeScript 类型
├─ utils/             # 工具函数
├─ views/             # 页面模块
├─ App.vue
└─ main.ts
```

目录将在项目初始化后按实际需求创建，不提前增加空目录。

## 开发约定

- 开发任何页面或组件前，必须先在 组件目录下的`requirements.md` 下编写对应的业务模块需求文档，需求明确后才能开始编码。
- 需求文档应至少说明功能目标、使用场景、字段与展示内容、交互规则、状态处理、接口依赖和验收标准；需求变化时应先更新文档。
- 统一使用 Vue Composition API、`<script setup lang="ts">` 和明确的 TypeScript 类型，原则上不使用 `any`。
- 使用 ESLint 检查代码质量、Prettier 统一格式，提交前必须通过格式化、代码检查和类型检查。
- 组件使用 `PascalCase` 命名，composable 使用 `useXxx` 命名；导入统一使用 `@/` 路径别名。
- `views` 下每个页面使用独立目录，入口统一为 `index.vue`；页面专属代码就近放置，跨页面复用后再提升至公共目录。
- 页面负责业务编排，不同业务职责拆分为独立组件，通用逻辑提取至组件或 composable。
- 开发时坚持最小化改动，不顺带重构或格式化无关代码，并保持已有组件 API、接口和路由兼容。
- 优先复用已有能力并消除重复，但避免过早抽象；仅将职责明确、接口稳定且确有复用价值的能力提升为公共模块。
- Lodash 工具统一维护在 `src/utils/lodash.ts`，格式化方法统一维护在 `src/utils/format.ts`，并通过 `src/utils/index.ts` 对外导出。
- 修改公共模块前应检查所有调用方；新增依赖或进行大范围结构调整前必须先说明影响并确认。
- 单个源代码文件尽量不超过 400 行，按职责合理拆分，避免仅为控制行数而拆分。
- 新增或修改的函数必须添加用途注释；`if/else` 等条件分支应对判断目的、业务原因或特殊边界添加必要注释。源代码注释行数占非空代码行数的比例必须超过 10%，且不得通过无意义注释凑数。
- 所有请求统一托管在 `src/api/` 下并按业务模块组织，页面和组件不得直接使用 Axios、请求实例或全局 `$http`。
- 页面仅调用 API 模块对外暴露的业务请求函数；每个请求应注释用途、参数和返回数据结构，并为请求、响应和分页结构定义明确类型。
- 需要取消重复请求时由 API 方法显式设置 `autoCancel`；默认关闭，`true` 使用 URL 作为 key，字符串使用自定义 key，函数可根据请求配置生成 key。
- 临时状态保留在组件内，跨组件逻辑优先使用 composable，确需跨页面共享时才使用 Pinia。
- Pinia store 按职责拆分为独立模块，例如 `theme`、`user`；禁止将无关的全局状态集中到单一 app store。
- 表单应统一处理初始值、校验和重复提交；表格应统一查询、分页、排序及异常状态。
- 路由名称保持唯一，页面标题、权限等信息统一维护在路由 `meta` 中。
- 路由分为全屏布局和主布局：登录、404 等页面使用全屏布局，业务页面统一作为主布局的子路由，并使用头部、左侧菜单和内容区域。
- 页面文案通过国际化语言包管理；颜色、间距和字号使用设计令牌或 CSS 变量。
- 代码应覆盖加载、空数据、无权限和请求失败等状态；复杂工具函数与 composable 应补充必要测试。
- 不使用忽略类型、关闭检查规则、吞掉异常或硬编码模拟数据等方式掩盖问题；未执行的检查不得声称通过。
- Git 提交信息遵循下方的 Conventional Commits 约定。

### Git 提交信息约定

提交标题格式为 `type(scope): subject`，其中 `scope` 可选，`subject` 应简洁说明本次变更目的。提交信息使用小写英文前缀，避免使用无意义的 `update`、`修改` 等描述。

| 前缀        | 使用场景                           | 示例                                         |
| ----------- | ---------------------------------- | -------------------------------------------- |
| `feat:`     | 新增功能或用户可见能力             | `feat(dataset): add dataset store`           |
| `fix:`      | 修复缺陷或错误行为                 | `fix(auth): refresh user after cookie login` |
| `refactor:` | 重构代码但不改变既有功能           | `refactor(utils): simplify tree traversal`   |
| `docs:`     | 仅修改文档                         | `docs: add frontend conventions`             |
| `style:`    | 仅调整格式、空白或样式，不改变逻辑 | `style: format source files`                 |
| `test:`     | 新增或修改测试                     | `test(utils): cover tree filtering`          |
| `chore:`    | 工具链、依赖或工程配置维护         | `chore: update eslint config`                |
| `build:`    | 构建脚本或打包配置变更             | `build: adjust vite target`                  |
| `ci:`       | 持续集成流程变更                   | `ci: run type check in pipeline`             |

一次提交应尽量只包含一个明确目的；需求实现、无关重构和大范围格式化不要混在同一提交中。

### 需求文档约定

页面和组件需求文档统一放在 `docs/requirements/<业务模块>/` 下，文件名使用 kebab-case，并尽量与对应页面或组件名称保持一致。页面拆分出的子组件可以记录在页面需求文档中；具有独立业务职责或被多个页面复用的组件应使用独立需求文档。
